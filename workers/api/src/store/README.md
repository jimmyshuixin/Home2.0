# Storage adapters and Google service-account OAuth

`Store` persists private application records under `collection/id`. All reads inside a transaction must complete before any put/delete. Transaction callbacks may be re-run on explicit database contention and must not send email, upload media or perform other external side effects. Put captures an immutable serialized value; a transaction handle becomes unusable when the callback ends.

## Adapters

- `MemoryStore(seed?)`: deterministic test adapter only. The application must never choose it as an unconfigured production fallback.
- `SqliteStore(filename)`: real local Node `node:sqlite` persistence, WAL, FULL synchronous mode and BEGIN IMMEDIATE transactions. All in-process connections to the same canonical file share a queue; SQLite locking also protects against other processes. Transient lock contention gets bounded retries. Call `await close()` before removing a test database. This file is Node-only and must not be imported into the Worker bundle. Node 22.23.2 marks its SQLite API experimental.
- `FirestoreStore({projectId,databaseId,edition:'standard',collectionPrefix?},{getAccessToken,fetch?,timeoutMs?,maxAttempts?})`: fixed Google REST endpoints, explicit Standard/Native configuration, `v3_` namespace by default. A different prefix must still begin with `v3_`. Missing or unsupported configuration fails closed. It never selects a Firebase project, provisions infrastructure, reads the legacy guestbook, or migrates data automatically.

Firestore stores `record_json.stringValue` and `schema_version.integerValue=1` in each private document. This isolates the application JSON schema from Firestore-specific value encoding. It is not a queryable public projection. `list` orders by document ID, requests at most five records per upstream query, and reuses readTime while assembling one page. Public filtering and safe projection belong in repositories/routes.

The fixed `queryMedia` exception uses the private `media_catalog` projection. Every `media/<id>` transaction write also updates this catalog atomically; verified, active files also update a SHA-256 lookup in `media_hashes`. Catalog documents additionally store single-field `sort_created`, `sort_name`, and `sort_size` strings with an ID suffix for stable ordering. A query uses one of these fields only and needs no composite index. Filename ordering is case-insensitive Unicode ordering, not locale/pinyin collation. Other media filters are applied to a bounded 48-record ordered scan. An empty filtered page with a continuation cursor does not mean there are no more matches. Changing filters or ordering invalidates the cursor.

Before using the catalog, `MediaLibrary.advanceCatalog()` backfills five legacy media records per call, using fresh transaction reads. New writes maintain the projection during this migration. Until the persisted catalog state is ready, library reads report `catalogReady: false` rather than omitting old records. Duplicate lookup rechecks the actual media status, lifecycle, kind, size and verified hash; a stale hash pointer never authorizes reuse. Deleted media retain tombstones but leave the catalog.

## Public comment catalog and rollout

Every transaction put/delete of `public_comments/<id>` also maintains `public_comment_catalog/<id>` atomically. The catalog contains only the approved comment's ID, nickname, body, target and normalized creation time; no private moderation fields. Each projection is bounded to 16 KiB. Firestore additionally stores `sort_target`, a single string containing target type, target ID, UTC time and unique ID. `queryPublicComments` applies both target range bounds and descending ordering to this same field, with one request for at most `limit + 1` rows (default 20, maximum 50). It uses the automatic single-field index, not a manually provisioned composite index. The generic five-record `list` batching remains unchanged.

`PublicComments.advanceCatalog()` re-reads and projects at most five old JSON-only `public_comments` records per call. Its versioned checkpoint is `system/public_comment_catalog_v1`; concurrent calls cannot skip steps. Source rows are re-read inside the transaction so moderation after the scan cannot resurrect hidden comments. New approvals maintain their own projection even if their ID is behind the migration cursor or arrives after the last scanned page.

The administrator uses GET `/api/v1/admin/comments/catalog` and POST `/api/v1/admin/comments/catalog/advance` (empty JSON object, authenticated session, CSRF and trusted Origin). The moderation panel advances sequential bounded steps, permits pause/retry and retains the server checkpoint. While `ready=false`, public reads keep the legacy bounded ID-order scan and explicitly return `meta.catalogReady=false`; this phase is compatibility behavior, not the completed pagination fix. Once `ready=true`, public queries switch to target/time ordering. Cursors are bound to the target and query mode; refresh after the one-time legacy-to-catalog transition. Neither mode exposes private comment fields.

Deploy the transaction projection and bounded migration endpoints together, then finish migration with the authenticated moderation panel. Delivery is incomplete until the persisted catalog reports ready and anonymous reads verify newest-first target filtering, requested limits and cursor continuation. Do not reset the checkpoint or deploy an older API that writes public comments without maintaining the catalog after marking it ready. Public comment responses remain `no-store` so hiding is immediately reflected by subsequent reads, without a stale cache invalidation window.

Permanent deletion uses a resumable reference-check task, not a collection-wide Worker request. During its 15-minute check/confirmation window, a shared lifecycle fence pauses record saves and candidate creation. Existing public reads continue. Cancelling or expiration releases this pause. Confirmation turns the target into a `purging` tombstone and releases the global fence, so unrelated editing continues during cleanup retries. Saved media references are checked in batches of 100 (maximum 2000 distinct references per save), and the final save transaction verifies the lifecycle epoch has not changed. Each cleanup step aborts one known failed-processing multipart or deletes one owned R2 object and verifies its absence. The final transaction changes the tombstone to `deleted` and deducts used and verified reserved bytes exactly once. See [failed media recovery](../../../../docs/v3/FAILED-MEDIA-RECOVERY.md). No automatic retirement of historical revisions/releases or cleanup of unconfirmed failed processing reservations is implied.

Standard edition automatically indexes fields; the deployment configuration should exempt `record_json` from single-field indexing because this adapter never queries its contents. Expiry maintenance uses the default single-field `expires_at` index and does not enable Firestore TTL or provision a paid service.

## Expiry maintenance

Only `sessions`, `rates`, and public-submission `idempotency` receipts participate. Every transaction write stores a valid positive, safe-integer `expiresAt` as the original document's numeric `expires_at` field, alongside `record_json`. This adds no index document or extra document write. Whole-document updates remove that field when expiry becomes invalid; deletes remove the source and its indexed value together. Invalid/missing expiry remains stored and is never a deletion candidate. Other collections, including `auth_epochs`, uploads/upload requests, release idempotency, comments, contacts, revisions and releases, are excluded even if they contain an `expiresAt`. SQLite stores the same projection in an indexed nullable column; MemoryStore seed data intentionally represents legacy, unprojected records.

`ExpiryMaintenance(store, now).getStatus()` returns aggregate progress, budget and retry time without record identifiers or payloads. `advance()` claims a 120-second lease in `system/expiry_maintenance_v1` and performs at most one page. Initial backfill visits the three allowlisted collections in ID order, at most five source rows plus one lookahead per call. It re-reads every source inside the commit transaction before writing the projection, so a renewal/edit/deletion between scan and commit cannot be overwritten or resurrected. The cursor and aggregate counts commit atomically with the projections. Concurrent new writes are projected immediately even behind the cursor. Do not roll back to writers without this projection after completing backfill.

After backfill, one `queryExpired` request selects only `expires_at` and document names, ordered ascending on that field, with a maximum of six rows. Its implicit document-ID tie-break needs no composite index. One transaction batch-reads the checkpoint and at most five source documents, then verifies the lease token, lease time and each record's actual current expiry against a fresh clock reading before deleting. Renewed records are preserved and their projection refreshed. Invalid values are retained, removed from the candidate index and counted once when encountered; backfill's invalid count is a historical total, not a live unresolved-record inventory. No session identifier appears in status or logs.

Each step handles one collection, rotating through all three. At the end of a three-collection round, another round is immediately available if a query saw further candidates; otherwise maintenance pauses for one hour. `cleanup.lastCompletedAt` means the most recent completed round, not proof that no records can subsequently expire. Failures retain the lease until expiry and retain the charged allowance. An expired or replaced token cannot commit a stale page. A lost acknowledgement after final commit cannot increment counters or repeat deletion when the caller resumes: source changes and checkpoint are one transaction.

The shared UTC budget permits 192 reserved steps per day. Each claim conservatively reserves 42 document-read units, seven document-write units and five delete units: daily limits are 8064 / 1344 / 960. Backfill also reserves delete units even though it deletes nothing, deliberately leaving budget unused rather than claiming exact billing. Rollover moves only to a later UTC date; a clock rollback does not reset allowance. Reservations cover the bounded scan and up to five transaction attempts; read-only status calls, busy/limited competing claims, token issuance, unrelated business requests and provider billing specifics are outside these estimates. These values are cost guards, not total-account quota or billing guarantees. The configured scheduled worker advances one page per invocation, and the authenticated administrator can use remaining daily allowance.

`Transaction.getMany` keeps the same snapshot, 100-key bound, duplicate slots, read-before-write requirement and closed-handle checks as `get`. Firestore sends its keys in one `batchGet` with the transaction token. A typical maintenance step needs seven to eight Firestore HTTP calls (claim transaction, bounded query, final transaction), plus token acquisition when needed. Provider contention and failure handling increase that number, so no absolute subrequest guarantee is claimed. An unavailable/ambiguous commit is not automatically replayed; the lease/checkpoint lets a later caller safely resume. The application lifecycle still independently enforces session expiration and limit windows; maintenance only reclaims stored records. Expired idempotency receipts never authorize overwriting an existing business submission; the submission route must continue protecting the persistent business ID.

## Statistics bootstrap and correction

`system/statistics` is an explicitly initialized, versioned projection maintained in the same transactions as content creation, first idempotent submission and pending-comment moderation. Its absence means unknown: the statistics endpoint returns null counts and never scans the database. Updating a draft does not increase the content count.

Before initializing an existing namespace, pause admin writes and anonymous submissions. Call `statisticsRebuildPage(store, collection, cursor?)` from `records.ts` separately for creations, albums, fitness, playlists, comments and contacts; persist the running sums and returned cursors in a trusted operator runner. Each call fetches one page of at most 50 records. Continue a collection until nextCursor is null; count comments only when pending. Do not put that loop into one HTTP Worker request. For a newly verified empty namespace the operator may explicitly supply six zero counts instead of scanning, but code must never infer this from a missing statistics document.

After all pages are accounted for, call `installStatisticsProjection(store, counts, expectedVersion, trustedNow)`. Supply null only when no valid projection exists. If a valid projection existed, capture its version before scanning and pass that version: any intervening counted write makes installation fail with VERSION_CONFLICT. Uninitialized writes do not increment a projection, so the maintenance pause is mandatory for that initial scan. Resume writes only after installing the result. This procedure writes only the V3 namespace chosen by the operator; it does not inspect or count legacy records. No bootstrap or correction is performed automatically by the request factory.

Only an explicit Firestore ABORTED response triggers transaction retry with fresh reads. A transport failure during commit is ambiguous and is returned as unavailable without replaying the callback. The client's retry must use the original idempotency key so the application can retrieve an already-committed result. Rollback is awaited best effort and does not mask the original error.

## Data boundary

Storage rejects values that JSON would silently change or drop: undefined, NaN/Infinity, unsafe integers, BigInt, Dates, Maps/classes, getters, symbols, sparse arrays and cycles. Records must be no larger than 900 KiB of UTF-8 JSON and must have bounded depth/size. `get<T>` is a caller-provided business type, not runtime schema validation; routes/repositories must use the shared Zod schemas when accepting data and before producing public output.

List limits are 1–50 (default 20). Cursor tokens are validated and bound to the collection. Keys never permit slashes in IDs, traversal, arbitrary collection nesting or interpolated SQL. All SQLite values are bound parameters. Provider errors and bodies are not exposed.

## OAuth

`createGoogleAccessTokenProvider({projectId,clientEmail,privateKey},{scopes?,fetch?,now?,timeoutMs?})` returns an async token getter. Create it inside each Worker request factory; it reuses a token/signing key and de-duplicates issuance within that factory, without a module-level pending I/O promise. Default scope is only `datastore`. Key import/JWT signing use jose RS256, a fixed token endpoint/audience, one-hour assertions, bounded requests/responses, and token refresh at least 60 seconds before expiry.

For the present Firestore + Identity Platform admin account lookup/update path, explicitly select `GOOGLE_OAUTH_SCOPES.datastore` and `GOOGLE_OAUTH_SCOPES.identityToolkit`. The Identity Platform account lookup API documents identitytoolkit/cloud-platform scopes and the IAM permission `firebaseauth.users.get`. OAuth scopes do not grant IAM permissions, and `firebase` alone must not be assumed to authorize those methods. Configure only the additional IAM operations actually needed for account lookup/update and Firestore CRUD. Do not grant project Owner merely to make an adapter work.

No service-account key, production token, Firestore project data or actual network call is used in the adapter tests. OAuth tests generate a temporary RSA key in process. Firestore tests verify the REST protocol with injected fetch, including missing documents, fresh-read contention retries, ambiguous commits, rollback, namespace isolation and bounded pagination. They do not certify the actual project's edition, IAM, region, backup state, latency or bill.
