## 实际 Nuxt 发布链路

证据位于仓库忽略目录 `.private-build/release-integration-FRNxJE/result.json`，同目录包含真实磁盘 `fixture.sqlite`，两个候选各自有私有 snapshot、manifest 和 build.log。

| 本地候选 | 状态 | 实际文件数 | 实际总字节 | 生成、上传、校验耗时 |
|---|---|---:|---:|---:|
| `e666c6ff-66bb-4d89-9e0f-6506ee6a9029` | ready 后激活，再回滚恢复 | 45 | 582,982 | 32,705 ms |
| `45ec0a9b-c0d9-4498-8305-a99292f79260` | 隐藏内容的 ready 候选，曾激活 | 43 | 576,083 | 30,309 ms |

这些是明确标记的本地测试内容与实际测量值，不能当成真实访问量、站点内容或远端性能指标。测试读取的 Git HEAD 为 `685e73c653e6f6cc08bd4b7e30308bcb376421ab`，同时使用当前未提交实现；该值只是 fixture 的版本一致性输入，不是已核实的部署版本。

链路使用实际 Hono 路由、真实 `SqliteStore`，以及本地 Miniflare/workerd 的 R2 条件写、SHA 校验和 HTMLRewriter。管理员身份是专用注入 fixture；请求地址仅作为 URL 输入直接交给本地 Hono，不访问该远端域名。

Node 没有 Worker 的 HTMLRewriter，且 Node 流经过 Miniflare JS proxy 会丢失 native known-length 标记。测试桥因此把 HTML 重写和受 25 MiB 限制的静态文件请求送入同一 workerd 的原生 API。R2 仍执行 `put(request.body, onlyIf + sha256)`，没有绕过摘要或条件写，也没有修改生产上传路由。这个桥是测试运行环境适配，不是生产处理实现。

验证顺序是：后台保存 → 候选冻结 → 真实 Nuxt 静态生成 → 实际上传与分批校验 → 受认证 HTML/JS 私密预览 → 匿名拒绝 → 激活和公开 API 版本一致 → 第二候选隐藏返回 404 → 恢复旧不可变候选 → 新构建失败后旧公开版仍可访问。失败上报另验证错误执行器拒绝、任意错误文本拒绝、同失败码幂等；重新打开 SQLite 句柄仍读到失败状态。
